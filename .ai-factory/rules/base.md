# Project Base Rules

> Auto-detected conventions from codebase analysis. Edit as needed.

## General Conventions

- One class per file.
- Do not write documentation (KDoc).
- Do not write comments for obvious things.
- Do not perform actions that were not requested.
- Use English for everything (code, comments, documentation, commit messages).

## Naming Conventions

- Files: PascalCase matching the public class name (e.g. `WippyLuaParserDefinition.kt`).
- Plugin-owned types are prefixed with `Wippy` (e.g. `WippyProjectService`, `WippyAnnotator`).
- Classes/objects/interfaces: PascalCase.
- Functions and variables: camelCase.
- Constants and PSI element type fields: UPPER_SNAKE_CASE.

## Module Structure

- `src/main/kotlin/com/github/xepozz/wippy/` — plugin source, organized by feature package:
  - `lang/` — WippyLua language: file type, parser definition, lexer adapter, highlighter, annotator, folding, brace matcher, commenter, PSI (`lang/psi`).
  - `lsp/` — LSP4IJ integration (socket server descriptor, support provider, settings, connection service).
  - `index/` — file-based index for registry entries (`WippyEntryIndex`, `WippyConfigUtil`).
  - `project/` — project/module detection, source root configuration, lock-file listeners.
  - `reference/`, `highlighting/`, `toolWindow/`, `run/`, `sdk/`, `services/`, `tool/`, `util/` — feature areas.
- `src/main/grammars/` — Grammar-Kit sources: `WippyLua.flex` (lexer), `WippyLua.bnf` (parser/PSI grammar).
- `src/main/gen/` — generated lexer/parser/PSI (Java); do not edit by hand, regenerated by `generateLexer` / `generateParser`.
- `src/main/resources/META-INF/` — `plugin.xml` and optional dependency config files.
- `src/test/kotlin/` — tests; `src/test/testData/` — test fixtures.

## Kotlin Best Practices

- Prefer `val` over `var` for immutability.
- Use scope functions (`apply`, `also`, `let`, `run`, `with`) appropriately to improve readability.
- Use expression bodies for simple functions.
- Prefer extension functions to utility classes.
- Use null-safety features effectively (`?.`, `?:`, `!!` only when absolutely necessary).

## LSP4IJ Integration

- Use `LanguageServerFactory` for server registration.
- Use socket-based `StreamConnectionProvider` for manual server starts (server listens on `localhost:7777`).
- Implement a `DocumentMatcher` to limit LSP activation to Wippy projects only (`wippy.lock`, `.wippy.yaml`, or `.wippy/` present).
- Prefer standard LSP features (folding, signature help, structure view) provided by LSP4IJ.
- Avoid direct dependency on LSP4J to prevent `ClassCastException`.

## Error Handling & Logging

- Use the IntelliJ Platform `Logger` (`com.intellij.openapi.diagnostic.Logger`) for diagnostics; do not use `println`.
- Surface user-facing messages via the `Wippy` notification group and `MyBundle` message keys, not hardcoded strings.

## Testing

- JUnit-based tests using the IntelliJ Platform test framework (`TestFrameworkType.Platform`).
- Place fixtures under `src/test/testData/`; coverage is tracked with Kover.
